The current-rule strip lights up wherever volume peaks — never where the failure rate does. The proposed-rule strip lights up only on the Jul 26 spike. The old rule measures traffic; the outage landed on a quiet day, so it never noticed.

Existing query vs. proposed query

The same alert, re-expressed. The current rule thresholds absolute volume on the total key; the replacement thresholds a failure rate — self-normalizing, so it means the same thing at 3 a.m. as at peak, and stays valid as iOS purchases grow.

Existing query

# thresholds total validation volume
sum(pbr>validate_purchase|ios, 4min) > 300

Measures traffic, not health: total ≈ 2× success (revalidation churn). Fires on busy hours, blind on quiet ones — it missed the Jul 26 outage entirely.

Proposed query

{ratio(
   rolling_sum(pbr>validate_purchase|ios|fail,    1800000),
   rolling_sum(pbr>validate_purchase|ios|success, 1800000)
)} >= 15%

Measures fail / (fail + success) over 30 min. Volume-weighted and seasonality-invariant; 0/0 → 0 so quiet periods stay silent.

Backtest: warn at 5% (crossed 22:29 UTC), page at 15% (crossed 22:38) — ~18 min into a 2-hour outage, and silent the other 27 days. Blind spot to close in a fast-follow: a total blackout (no traffic at all) reads as 0/0 → healthy, so pair it with a low-side floor on …|ios|success volume.

Source: gcp1-prod-0055 metrics API — pbr>validate_purchase|ios with |fail / |success, 60 s resolution. Old rule modeled as sum(total) over 4 min > 300; new rule as 30-min fail/(fail+success) ≥ 15%. Hover the chart for any hour.
